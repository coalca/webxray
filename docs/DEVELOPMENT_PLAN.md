# WebXray 0.2 development plan

## Product goal

WebXray should feel like one appliance instead of a separately deployed web
page and API. A new user opens the page, sees the control panel immediately,
and uses the connection control in the upper-right corner only when the API
address or access token needs attention.

The same application is delivered in three forms:

1. A Docker container for servers and NAS devices.
2. A Deb package with a managed systemd service for Debian and Ubuntu.
3. A portable Windows ZIP that can register or remove itself as a Windows
   service without an installer wizard.

The interaction model takes cues from
[AriaNg](https://github.com/mayswind/AriaNg): responsive, dense, status-first,
and able to connect to a configurable backend. The portable service workflow
takes cues from [ddns-go](https://github.com/jeessy2/ddns-go): extract one
archive and use a short `-s install` or `-s uninstall` command.

## User journeys

### First Docker run

1. Create one host directory.
2. Run one container with that directory mounted at `/data`.
3. Read `/data/config.json` for the generated access token.
4. Open the page, click the red connection indicator, and enter the token.
5. Add a server or subscription and start Xray.

### First Deb install

1. Download the package matching `amd64` or `arm64`.
2. Install it with `apt`; systemd starts WebXray automatically.
3. Read the token with `sudo webxray token`.
4. Open port 3000 in a browser and connect.

### First Windows install

1. Download and extract the x64 ZIP to a permanent directory.
2. Run an Administrator terminal in that directory.
3. Run `webxray.cmd -s install`; the command prints the token, registers the
   service, starts it, and opens the browser.
4. Keep the `data` directory when replacing application files during updates.

## Runtime contract

Every distribution resolves the following logical files:

| File | Purpose | User-owned |
| --- | --- | --- |
| `config.json` | Web port, access token, CORS, timezone | Yes |
| `state.json` | Profiles, subscriptions, routing and UI settings | Yes |
| `xray/xray` or `xray/xray.exe` | Xray executable | Yes after first copy |
| `xray/geoip.dat` | IP routing data | Yes after first copy |
| `xray/geosite.dat` | Domain routing data | Yes after first copy |
| `xray/config.json` | Last validated config generated by WebXray | Generated |
| `xray/config.candidate.json` | Configuration being validated | Generated |

Docker maps the table directly under `/data`. Deb stores it in
`/var/lib/webxray`. Windows stores it in the extracted `data` directory.
Bundled Xray files are copied only when missing, so a user replacement is not
silently overwritten.

## Delivery phases

### Phase 1: runtime layout

- [x] Define the cross-platform data layout.
- [x] Copy missing Xray and Geo files on first start.
- [x] Run validation and the core from the external data directory.
- [x] Return effective paths in authenticated status responses.
- [x] Cover first-copy and preserve-existing behavior with tests.

### Phase 2: connection-first UI

- [x] Render the main console before the backend is connected.
- [x] Add a red/green connection control to the upper-right corner.
- [x] Move API address and token into a connection dialog.
- [x] Keep Xray process status separate from API connection status.
- [x] Retry network failures while respecting an explicit manual disconnect.
- [x] Keep the current node, subscription, route, backup and log workflows.

### Phase 3: native services

- [x] Add a hardened systemd unit and Deb lifecycle scripts.
- [x] Add a portable Windows command with `-s` service actions.
- [x] Provide separate, obvious Windows entry points for direct and service modes.
- [x] Use WinSW to provide the Windows Service Control Manager protocol.
- [x] Bundle Node, Xray and Geo data in the Windows archive.
- [x] Keep application files separate from user data for in-place updates.

### Phase 4: release automation

- [x] Build Deb packages for amd64 and arm64.
- [x] Build a portable Windows x64 ZIP.
- [x] Inspect package contents in CI before publishing.
- [x] Upload native packages to GitHub Releases for `v*` tags.
- [x] Keep the existing date-versioned GHCR image pipeline.

### Phase 5: acceptance and release

- [x] Run all unit and syntax tests.
- [x] Build and start the real Docker image with a clean bind mount.
- [x] Verify the unauthenticated and authenticated UI at desktop and mobile
  widths.
- [x] Build native packages with the real upstream runtime archives.
- [x] Commit, tag `v0.2.0`, push, and verify both GitHub workflows.

## Release acceptance

- The first screen is always the main console.
- The upper-right indicator is green only after an authenticated API state
  request succeeds; otherwise it is red.
- A clean Docker mount visibly contains WebXray config, state, Xray, Geo files,
  and the generated Xray configuration after use.
- `apt install ./webxray_*.deb` creates and starts `webxray.service` without
  deleting `/var/lib/webxray` on removal.
- `webxray.cmd -s install` and `-s uninstall` work from an Administrator
  terminal without MSI, NSIS, or another installer UI.
- Release artifacts contain license notices and do not contain access tokens or
  user state.
